## Domain and acceptance implications

**DID.** The v0.7.0 source declares 12 stateful exported circuits (controller rotation/recovery, aliases, verification methods and relations, service changes, deactivate, Schnorr digest verification) and 12 pure authorization-digest circuits. Its imported `schnorr` module uses a private `getSchnorrReduction` witness and Jubjub curve operations. The current Rust runtime has Jubjub primitives, but that is not evidence that the complete imported module, witness contract and all DID exports already lower or prove. First compile unchanged source, register exact circuit inventory and typed diagnostics, then turn simulator cases into independent TS/native/recorded/replay comparisons. Prove and apply original security-critical authorized mutations and negative replay/wrong-key/malformed-reduction paths against the pinned ledger. Do not replace cryptographic verification with host-side trust. The DID package uses ledger-v8 **8.1.0** whereas the finished Rust milestone-2 runtime pins **8.0.3**; establish exact type/serialization/VM compatibility or deliberately upgrade the Rust pin before claiming ledger acceptance.

**Digital passport.** The integration root uses `include`, generic `VC`/`VP`/relations imports, nested structs and pure assertions over five committed claims, selective disclosure, age-threshold date witnesses, explicit holder binding and issuance/verification protocol envelopes. Preserve public input/result types and false-claim behavior. Compile the complete 17-file pinned closure unchanged; compare authoritative pure export metadata, direct output/errors for independent TS/Rust vectors, then package a generated Rust crate that a consumer can import. The current TS package consumer round trip and codec compatibility tests are useful reference cases, but its JS codec is not automatically a Rust wire codec. Cross-language byte tests are required where Rust exposes public codecs. No ledger application claim is needed for purely declared circuits; generated proof calls should be tested only for actual proof-required exports found by compiler metadata.

**ACC placeholder.** User clarified that Passport ACC is selected only after DID and digital passport adoption. Record candidate [`midnightntwrk/passport`](https://github.com/midnightntwrk/passport) and SDK consumer separately, but do not make its ledger-9-to-8 downgrade a Wave-0 blocker or claim that it is within the immediate 0.3.0 acceptance set. When selected, preserve WebAuthn/P-256 authentication and all original contract semantics; a protocol-level incompatibility would be an explicit later decision, never silently weakened.

3. **Digital passport second (or independent pure lane):** compile full integration closure, including exactly pinned `credential-compact` package bytes. Cover claims, date boundaries, presentation requests, private-part openings and protocol matching with independent original TS capture and direct Rust outputs/errors. 4. **0.3.0 acceptance:** exact original contract source pins, full export manifests, no fabricated proof metadata or omitted failed exports, meaningful negative auth/validation tests, packaged external Rust consumer, signed local gate receipts. Refresh upstream refs/releases at RC and identify changed source closure before retesting. User's 9/10 objective means these original target contracts must work materially as authored; sampled fixtures or partial API availability alone are insufficient.
